# Agent Prompt — Milestone 8: Vector Database (FAISS Integration)

## Context

This is the AI Research Assistant project (FastAPI backend, MongoDB, LangChain-based RAG pipeline). The following milestones are already complete:

- Milestone 1–2: FastAPI foundation, JWT auth, MongoDB integration
- Milestone 3–4: Paper upload and storage
- Milestone 5: PDF text extraction
- Milestone 6: Text chunking (chunks include `chunk_id`, `paper_id`, `page_number`, `section`, `text`)
- Milestone 7: Embedding generation (each chunk has a corresponding embedding vector)

**This milestone (8) implements the vector database layer using FAISS.**

## Important constraint to understand before building

FAISS only stores vectors and integer IDs — it has no native support for metadata, filtering by user/paper, or persistence beyond raw index files. All of that has to be built around FAISS explicitly. Do not treat FAISS as a drop-in database; treat it as a similarity-search primitive that needs a metadata layer wrapped around it.

## Goal

Build a `VectorDBService` that:
1. Stores chunk embeddings in a FAISS index
2. Maintains a metadata store mapping FAISS internal IDs → chunk metadata (`chunk_id`, `paper_id`, `user_id`, `page_number`, `section`, `text`)
3. Supports similarity search with optional filtering (by `user_id` and/or `paper_id`)
4. Persists the index and metadata to disk and reloads on startup
5. Supports deleting all vectors belonging to a given paper (for when a user deletes an uploaded paper)

## Design decisions to follow

- **Index type:** Use `IndexFlatIP` (inner product) with L2-normalized vectors, which is equivalent to cosine similarity. Do not use `IndexFlatL2` — cosine similarity is standard for sentence embeddings and this matters for retrieval quality. Wrap it in `IndexIDMap` so we can assign and later remove vectors by explicit integer ID instead of relying on insertion order.
- **ID strategy:** Generate a unique integer FAISS ID for each chunk (e.g., an auto-incrementing counter persisted alongside the index, or derive from a hash — auto-increment is simpler and preferred). Store the mapping `faiss_id → {chunk_id, paper_id, user_id, page_number, section, text}` in a separate metadata store.
- **Metadata store:** Use a local JSON or pickle file (e.g., `vector_store/metadata.pkl`) for now, keyed by `faiss_id`. Do NOT put this logic inside MongoDB for this milestone — keep it simple and file-based, matching FAISS's own persistence model. Note in code comments that this could move to MongoDB or Redis later if the app needs multi-instance deployment.
- **Filtering by user/paper:** Since `IndexFlatIP` doesn't support native metadata filtering, implement search as: (a) run the similarity search with a larger `k` than requested (e.g., `k * 5`), (b) post-filter results using the metadata store by `user_id`/`paper_id`, (c) truncate to the requested `top_k`. Document this tradeoff clearly in a code comment — this is fine at current scale but should move to per-user/per-project FAISS indices or a proper vector DB (Qdrant/Weaviate/pgvector) if the app scales significantly. Do not silently hide this limitation.
- **Persistence:** Save the FAISS index using `faiss.write_index()` / `faiss.read_index()`. Save metadata using pickle or JSON. Load both on app startup (in the FastAPI lifespan handler) if files exist; otherwise initialize an empty index.
- **Thread safety:** FAISS index writes are not thread-safe. Use a simple `asyncio.Lock` (or `threading.Lock` if calls are sync) around add/delete operations to prevent race conditions if multiple uploads happen concurrently.

## Required implementation

### 1. `rag/vector_store.py`

Implement a `VectorDBService` class with these methods:

- `__init__(self, dim: int, index_path: str, metadata_path: str)` — initializes or loads existing index + metadata
- `add_embeddings(self, embeddings: list[list[float]], metadata_list: list[dict]) -> list[int]` — normalizes vectors, adds to index with new FAISS IDs, stores corresponding metadata, returns assigned FAISS IDs
- `search(self, query_embedding: list[float], top_k: int = 5, user_id: str = None, paper_id: str = None) -> list[dict]` — normalizes query vector, searches, post-filters by `user_id`/`paper_id` if provided, returns list of `{faiss_id, score, chunk_id, paper_id, page_number, section, text}` sorted by relevance
- `delete_by_paper(self, paper_id: str) -> int` — removes all vectors belonging to a paper (via `IndexIDMap.remove_ids`), removes corresponding metadata entries, returns count removed. Note: FAISS `IndexFlatIP` supports removal via `IndexIDMap`; confirm this works in the actual FAISS version installed and handle the rebuild-index fallback if the installed version doesn't support `remove_ids` cleanly.
- `save(self)` — persists index and metadata to disk
- `load(self)` — loads index and metadata from disk if present
- `get_stats(self) -> dict` — returns total vector count, index size on disk, for a debug/admin endpoint

### 2. `services/vector_service.py`

Higher-level orchestration function(s) that:
- Take chunk + embedding output from Milestone 6/7 pipeline
- Call `VectorDBService.add_embeddings()` with properly formatted metadata
- Are called automatically at the end of the PDF processing pipeline once a paper finishes chunking + embedding

### 3. `api/search_routes.py`

A test endpoint to validate retrieval independent of the full RAG/LLM pipeline:
- `POST /search` — accepts `{query: str, top_k: int, paper_id: Optional[str]}`, embeds the query using the existing embedding model from Milestone 7, calls `VectorDBService.search()`, returns raw results with scores. This is a debugging/testing endpoint — it should require auth and scope results to the current user's `user_id` automatically (don't let users search other users' papers).

### 4. Startup/shutdown integration

In `main.py`'s lifespan handler:
- Initialize `VectorDBService` on startup (load existing index if present)
- Save index + metadata on shutdown (in addition to saving after every write, as a safety net)

### 5. Config additions

Add to `.env` / `settings.py`:
- `VECTOR_STORE_PATH=vector_store/faiss.index`
- `VECTOR_METADATA_PATH=vector_store/metadata.pkl`
- `EMBEDDING_DIM=<match your Milestone 7 embedding model's output dimension>`

## Testing requirements

Write `tests/test_vector_store.py` covering:
1. Adding embeddings and confirming they're retrievable via search
2. Search returns results ranked by similarity (test with a known-similar and known-dissimilar pair)
3. Filtering by `paper_id` correctly excludes other papers' chunks
4. `delete_by_paper` removes vectors and they no longer appear in search results
5. Index persists correctly across a save/load cycle (create, save, reload in a new instance, confirm search still works)

## Manual verification steps (do these after implementation)

1. Upload two different papers through the existing pipeline (Milestones 4–7).
2. Confirm both get chunked, embedded, and their vectors land in the FAISS index (`get_stats()` should reflect the total chunk count).
3. Hit `POST /search` with a query relevant to only one of the papers — confirm it returns higher-scored results from the correct paper.
4. Hit `POST /search` with `paper_id` filter set — confirm results are scoped correctly.
5. Restart the FastAPI server — confirm the index reloads from disk and search still works without re-uploading.
6. Delete one paper via the existing delete endpoint — confirm its vectors are removed from search results afterward.
