# Milestone 23 — Research Assistant UI

## Project Context

I am building an **AI Research Assistant** application.

The project is an AI-powered research platform where users can:

* Upload research papers/PDFs
* Store and manage papers
* Extract and process paper content
* Generate embeddings
* Perform RAG-based question answering
* Ask questions about research papers
* Receive grounded answers
* View citations and source sections
* Summarize research papers
* Compare multiple papers
* Maintain research conversations/history

The project already has a working backend and frontend foundation.

### Completed Milestones

Milestones 1–21 have already been completed.

Important completed functionality includes:

1. Project setup
2. Authentication
3. Workspace
4. PDF upload
5. Text extraction
6. Text chunking
7. Embedding generation
8. Vector database
9. RAG question answering
10. Autonomous LangGraph agent
11. Citation and source grounding
12. Advanced paper summarization
13. Multi-paper comparison
14. Advanced research functionality
15. Additional research-agent functionality
    16–21: backend/research workflow improvements and preparation for frontend/deployment

### Milestone 22

Milestone 22 established the **Frontend Foundation**.

The existing frontend architecture, routing, authentication handling, API layer, components, styling system, and layout must be inspected and reused.

Do NOT unnecessarily rewrite the existing frontend architecture.

---

# OBJECTIVE

Implement **Milestone 23 — Research Assistant UI**.

The objective is to create the first complete usable research workflow in the frontend.

The user should be able to:

1. Open the research workspace
2. View their uploaded research papers
3. Upload a new paper
4. See paper processing status
5. Select/open a paper
6. View paper details
7. Ask research questions
8. Receive answers from the existing RAG backend
9. View citations/source references
10. Continue a research conversation
11. View previous conversation/history
12. Handle loading, empty, and error states properly

This milestone should make the application feel like a real working AI Research Assistant rather than only a frontend shell.

# MAIN FEATURES

## Feature 1 — Research Workspace

Create the main research workspace page.

The workspace should contain:

### Sidebar / Paper Library

Display:

* Research papers
* Paper title
* Upload date
* Processing status
* Optional file type/page count if available
* Search/filter capability if already supported by backend

Possible states:

### Loading

Display a proper loading state while papers are being fetched.

### Empty

If the user has no papers:

Display a helpful message such as:

"No research papers yet"

and provide:

"Upload Paper"

button.

### Error

If the API fails:

Display a user-friendly error message and retry option.

---

# Feature 2 — Upload Research Paper

Implement the frontend upload workflow using the existing backend upload API.

Requirements:

* File picker
* PDF validation
* Upload progress/loading state
* Disable duplicate submissions while uploading
* Display success/error feedback
* Refresh paper library after successful upload

Do not create a new backend upload endpoint if one already exists.

Use the existing authentication mechanism.

---

# Feature 3 — Paper Processing Status

Research papers may go through multiple processing stages.

Use the actual status returned by the backend.

For example, if the backend already provides statuses such as:

* uploaded
* processing
* embedding
* ready
* failed

display those appropriately.

Do NOT invent statuses that do not exist in the backend.

The UI should clearly communicate when a paper is:

* Still processing
* Ready for research
* Failed

If polling is already supported/appropriate, implement polling carefully.

Avoid unnecessary API requests.

---

# Feature 4 — Paper Details

When a user selects a paper, display a paper details view.

Include information available from the backend, such as:

* Paper title
* Metadata
* Upload date
* Processing status
* Authors
* Abstract
* Page count
* Other available metadata

Only display fields that actually exist.

Do not fabricate missing metadata.

---

# Feature 5 — Research Q&A

Implement the main research question-answering interface.

The user should be able to type a question such as:

"What methodology does this paper use?"

or:

"What are the main limitations discussed by the authors?"

or:

"What datasets were used?"

The question should be sent to the existing RAG/research API.

The response should be displayed clearly.

---

# Feature 6 — Chat Interface

Create a clean research conversation interface.

Messages should visually distinguish:

### User message

The question asked by the user.

### Assistant message

The answer generated by the research backend.

Each conversation should preserve message order.

The UI should automatically scroll to the latest message when appropriate.

---

# Feature 7 — Citations and Sources

This is a critical feature.

The AI Research Assistant must show the sources used to generate the answer whenever the backend provides them.

For each citation/source, display available information such as:

* Source number
* Paper name
* Relevant text/chunk
* Page number
* Section
* Citation metadata

Example UI:

> Answer generated from sources

**[1] Page 4 — Methodology**

Relevant source excerpt...

**[2] Page 7 — Experiments**

Relevant source excerpt...

Do not create fake citations.

If the backend does not return a particular field, do not display an invented value.

---

# Feature 8 — Source Interaction

Make citations interactive where possible.

For example:

Clicking a citation/source should:

* Expand the source
* Show the relevant excerpt
* Display page/section information if available

Keep the implementation compatible with the existing backend response.

Do not implement PDF highlighting unless the existing backend/frontend architecture already supports it.

That functionality can be expanded in a later milestone.

---

# Feature 9 — Conversation History

Use the existing conversation/history APIs.

Users should be able to view previous research conversations.

Display available information such as:

* Conversation title
* First question
* Last updated time
* Associated paper/workspace
* Number of messages if available

Clicking a conversation should load its messages.

Do not create fake conversation records.

---

# Feature 10 — New Conversation

Provide a clear action for:

"New Research Session"

or equivalent.

Starting a new session should:

* Clear the current conversation state
* Preserve the selected paper
* Allow the user to ask a new question
* Create/use the backend conversation according to the existing API design

Do not create a separate frontend-only conversation system.

---

# Feature 11 — Loading States

Every asynchronous operation should have a proper loading state.

Examples:

* Loading papers
* Uploading paper
* Processing paper
* Loading paper details
* Sending question
* Loading conversation
* Loading citations

Avoid freezing the entire application unnecessarily.

Use localized loading indicators wherever possible.

---

# Feature 12 — Error Handling

Handle API failures gracefully.

Examples:

* Upload failure
* Unauthorized request
* Paper not found
* RAG failure
* Conversation loading failure
* Network failure
* Backend unavailable

Display human-readable errors.

Do not expose raw stack traces to users.

Provide retry actions where appropriate.

---

# Feature 13 — Authentication

Use the authentication mechanism implemented in previous milestones.

Every protected API request must correctly include the required authentication credentials/token.

Handle:

* Expired authentication
* Unauthorized API response
* Redirect to login if that is how the existing application works

Do not introduce another authentication mechanism.
