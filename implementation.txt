============================================================
3. WHY CHUNKING IS NEEDED
============================================================

Do NOT simply concatenate the entire research paper and
store it as one chunk.

A 30-page research paper may contain thousands of tokens.

Embedding an entire paper as one vector would reduce retrieval
precision.

Instead:

Full Paper
 ↓
Smaller meaningful chunks
 ↓
Each chunk later becomes an embedding
 ↓
Vector database
 ↓
Semantic retrieval

Chunking therefore directly affects future RAG quality.

============================================================
4. CHUNKING STRATEGY
============================================================

Implement a configurable recursive chunking strategy.

Use:

RecursiveCharacterTextSplitter

from:

langchain_text_splitters

Do not hardcode the chunk size in the service.

Configuration should come from environment variables.

Recommended initial values:

CHUNK_SIZE=700
CHUNK_OVERLAP=100

These are starting values and must be easy to change.

Do NOT claim that 700/100 is universally optimal.

We will evaluate and tune these values later.

============================================================
5. WHY RECURSIVE CHARACTER SPLITTER
============================================================

Use RecursiveCharacterTextSplitter because it attempts to
split text at increasingly smaller boundaries.

Conceptually:

Paragraph
 ↓
Sentence
 ↓
Words
 ↓
Characters

It tries to keep meaningful text together before making
smaller splits.

The goal is to avoid arbitrary cutting whenever possible.

============================================================
6. SEPARATORS
============================================================

Configure separators appropriately for research papers.

Prefer a hierarchy similar to:

1. Paragraph boundaries
2. Line boundaries
3. Sentence-like boundaries
4. Word boundaries
5. Character boundaries

Do not use an unnecessarily complex custom parser.

The implementation should remain maintainable.

If LangChain's default separators are sufficient, use them.

If customization is necessary, explain why.

============================================================
7. TOKEN VS CHARACTER CHUNK SIZE
============================================================

IMPORTANT:

LangChain's RecursiveCharacterTextSplitter primarily uses
character length unless configured differently.

Do NOT incorrectly claim:

CHUNK_SIZE=700 means exactly 700 tokens.

Instead, clearly document that the initial configuration is
character-based unless a token-aware splitter is deliberately
implemented.

If the existing project already has a tokenizer that can be
safely reused, evaluate whether token-based chunking provides
a meaningful advantage.

For this milestone:

Start with RecursiveCharacterTextSplitter.

Keep the architecture flexible enough to change the strategy
later.

============================================================
8. CHUNK OVERLAP
============================================================

Implement:

CHUNK_OVERLAP=100

The overlap helps preserve context between neighboring chunks.

Conceptually:

Chunk 1:
A B C D E F G

Chunk 2:
F G H I J K L

F and G provide contextual overlap.

Do not use excessive overlap.

Overlap must always be smaller than chunk size.

Validate configuration:

chunk_overlap < chunk_size

If invalid:

fail configuration validation with a clear error.

============================================================
9. PAGE BOUNDARY PRESERVATION
============================================================

This is CRITICAL.

Do not lose page information.

The chunking pipeline must preserve:

page_start
page_end

Example:

Chunk 1:

{
    "page_start": 1,
    "page_end": 1
}

Chunk 2:

{
    "page_start": 1,
    "page_end": 2
}

A chunk may span multiple pages.

Therefore do not assume:

one chunk = one page.

The correct relationship is:

Paper
 ↓
Pages
 ↓
Chunks

A chunk may reference one or multiple pages.

============================================================
11. CHUNK INDEX
============================================================

Chunk indexing must be deterministic.

Example:

chunk_index:

0
1
2
3
...

Do not use random chunk indexes.

The chunk_id itself can be UUID/ObjectId.

But chunk_index should represent the ordering of chunks
within a paper.

Example:

Paper A:

chunk_index = 0
chunk_index = 1
chunk_index = 2
...

============================================================
12. CHUNK ORDER
============================================================

Chunks must preserve document order.

For example:

Page 1
 ↓
Page 2
 ↓
Page 3

must become:

Chunk 0
 ↓
Chunk 1
 ↓
Chunk 2

Do not sort chunks alphabetically.

Do not randomly reorder chunks.

============================================================
13. PAGE-AWARE CHUNKING
============================================================

Do NOT blindly process every page independently.

Bad approach:

Page 1 → chunks
Page 2 → chunks
Page 3 → chunks

This can cause poor context when a paragraph continues across
pages.

Instead, construct the source text in document order while
retaining page boundary information.

Then create chunks.

After generating each chunk, determine which source pages
contributed to that chunk.

Store:

page_start
page_end

If exact page attribution becomes technically difficult,
implement a deterministic mapping based on character offsets.

Do not guess page numbers.

============================================================
14. CHARACTER OFFSET MAPPING
============================================================

Prefer maintaining source offsets.

Example source:

Page 1:

characters 0–5000

Page 2:

characters 5001–10000

Page 3:

characters 10001–15000

After chunking:

Chunk 0:

characters 0–700

→ page_start = 1
→ page_end = 1

Chunk 1:

characters 600–1300

→ page_start = 1
→ page_end = 1

Chunk 10:

characters 4900–5600

→ page_start = 1
→ page_end = 2

This provides reliable page attribution.

Implement the simplest reliable approach compatible with
the existing Milestone 5 data model.

============================================================
21. REPROCESSING / IDEMPOTENCY
============================================================

This is critical.

If the user calls:

POST /papers/{paper_id}/chunks

twice:

DO NOT create duplicate chunks.

Choose a consistent strategy.

Recommended:

1. Delete existing chunks for that paper.
2. Re-run chunking.
3. Insert new chunks.
4. Update chunking status.

This ensures the database reflects the current extraction.

However, perform this safely so that a failed reprocessing operation
does not unnecessarily destroy the previous successful result.

If a transactional strategy is practical, use it.

Otherwise implement a safe replace strategy and explain it.

31. API ENDPOINT
============================================================

Create:

POST /papers/{paper_id}/chunks

Authentication required.

Workflow:

1. Authenticate user.
2. Find paper.
3. Verify paper ownership.
4. Verify text extraction completed.
5. Retrieve extracted text/pages.
6. Validate that text exists.
7. Update chunking status to "chunking".
8. Build ordered source text.
9. Preserve page offsets.
10. Initialize LangChain splitter.
11. Split text.
12. Determine page_start/page_end for each chunk.
13. Create chunk metadata.
14. Store chunks in MongoDB.
15. Update status to "completed".
16. Return chunk statistics.

Response:

{
    "message": "Paper chunked successfully",
    "paper_id": "...",
    "chunk_count": 42,
    "chunk_size": 700,
    "chunk_overlap": 100,
    "status": "completed"
}
