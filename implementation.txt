# Agent Prompt — Milestone 9: RAG Pipeline (Question Answering with Citations)

## Context

This is the AI Research Assistant project (FastAPI backend, MongoDB, FAISS vector store). The following milestones are already complete:

- Milestone 1–4: FastAPI foundation, JWT auth, MongoDB integration, paper upload/storage
- Milestone 5–6: PDF text extraction, chunking (chunks include `chunk_id`, `paper_id`, `page_number`, `section`, `text`)
- Milestone 7: Embedding generation
- Milestone 8: FAISS vector database with `VectorDBService` (`add_embeddings`, `search`, `delete_by_paper`, filtering by `user_id`/`paper_id`)

**This milestone (9) builds the core RAG question-answering pipeline: retrieval → prompt construction → LLM call → structured, cited answer, plus chat history persistence.**

## Goal

Build a working `POST /chat` endpoint where a user asks a natural-language question about their uploaded paper(s) and receives:
1. An answer grounded strictly in retrieved paper content (no hallucination from the LLM's general knowledge)
2. Structured citations (paper name, page, section) tied to specific claims in the answer
3. Conversation memory within a project/workspace, so follow-up questions with pronouns ("compare **it** with GPT") resolve correctly
4. An explicit "not found in the provided papers" response when retrieval doesn't support an answer, instead of a guess

## Design decisions to follow

- **Citation format:** Use structured JSON output from the LLM, not marker-parsing of prose. Force the LLM to return `{answer, citations: [...]}` as JSON. This is more reliable to render in the frontend and reused later by Comparison/Literature Review agents — don't build a prose-marker parser instead.
- **Grounding enforcement:** The prompt must explicitly instruct the LLM to answer only from provided context and to say so if the context is insufficient. Additionally, add a **pre-LLM guardrail**: if the top retrieved chunk's similarity score is below a configurable threshold (e.g., 0.3 for cosine similarity), skip the LLM call entirely and return a "no relevant content found" response. Do not rely on the LLM alone to self-police low-relevance retrieval.
- **Chat history:** Store every turn in MongoDB (`chats` collection), scoped to `user_id` + `project_id` (or `paper_id` if no project concept exists yet). Include the last 3–5 turns in the prompt for follow-up context. Do not build a separate memory system — this is just prompt-included history.
- **Streaming:** Implement the LLM call with streaming (Server-Sent Events) so the frontend can render tokens as they arrive. Support a non-streaming fallback mode via a query param for simpler testing (e.g., `?stream=false`), since streaming complicates citation parsing (citations should arrive as a final structured block after the streamed answer text, not mid-stream).
- **Token/cost tracking:** Log prompt tokens, completion tokens, and model used for every request. Store this on the chat message document or in a separate `usage_logs` collection — needed for a future cost-tracking/rate-limiting feature and useful for debugging retrieval quality issues.
- **Model abstraction:** Do not hardcode calls to a single LLM provider's SDK directly in the route handler. Build a thin `LLMService` wrapper so swapping between OpenAI/Llama/Gemini later doesn't require touching the RAG logic.

## Required implementation

### 1. `rag/prompt_builder.py`

Implement `build_rag_prompt(question: str, retrieved_chunks: list[dict], chat_history: list[dict]) -> str` (or return a structured message list if using chat-style APIs):

- Format each retrieved chunk with a `[Source N]` label including paper name, page number, and section
- Include the last `CHAT_HISTORY_TURNS` question/answer pairs before the current question, clearly labeled as prior conversation
- Instruct the LLM to:
  - Answer only from the provided context
  - Explicitly state when context is insufficient rather than guessing
  - Return output as JSON matching a fixed schema: `{"answer": str, "citations": [{"source_index": int, "paper": str, "page": int, "section": str}]}`
- Keep the instruction block consistent and testable — this template will be extended (not rewritten) for Summary/Comparison agents later, so keep the grounding/JSON-output instructions in a reusable helper rather than duplicating them inline.

### 2. `services/llm_service.py`

Implement `LLMService` with:
- `generate(prompt, stream: bool = False)` — calls the configured provider (start with OpenAI; keep the interface provider-agnostic so Llama/Gemini can be swapped in via config)
- For streaming: yield tokens/chunks as they arrive (async generator)
- For non-streaming: return the full completion
- Return token usage metadata alongside the response (`prompt_tokens`, `completion_tokens`) for logging
- Handle and surface provider errors cleanly (rate limits, timeouts) rather than letting raw SDK exceptions bubble to the route handler

### 3. `rag/rag_pipeline.py`

Implement `run_rag_query(user_id: str, question: str, project_id: str = None, paper_id: str = None, top_k: int = 6) -> dict`:

1. Embed the question (reuse Milestone 7's embedding model — same model/preprocessing as chunk embeddings)
2. Retrieve top-k chunks via `VectorDBService.search()`, scoped to `user_id` and optionally `paper_id`/`project_id`
3. **Guardrail check:** if the top result's similarity score is below `RETRIEVAL_SCORE_THRESHOLD`, skip the LLM call and return `{"answer": "I couldn't find relevant content in your uploaded papers for this question.", "citations": []}` immediately
4. Load recent chat history via `chat_service`
5. Build the prompt via `prompt_builder.build_rag_prompt()`
6. Call `LLMService.generate()`
7. Parse the JSON response; if parsing fails, retry once with a stricter "return valid JSON only" follow-up instruction before falling back to a graceful error response (never crash the endpoint on malformed LLM output)
8. Return `{"answer": str, "citations": list[dict], "usage": {...}}`

### 4. `services/chat_service.py`

- `save_turn(user_id, project_id, question, answer, citations, usage)` — persists to MongoDB `chats` collection
- `get_recent_history(user_id, project_id, limit=5)` — retrieves last N turns, ordered chronologically, for prompt inclusion

### 5. `models/chat.py` and `schemas/chat_schemas.py`

- `ChatMessage` model: `id, user_id, project_id, question, answer, citations, usage, created_at`
- Request schema: `ChatRequest { question: str, project_id: Optional[str], paper_id: Optional[str], top_k: Optional[int] = 6 }`
- Response schema: `ChatResponse { answer: str, citations: List[Citation], usage: UsageInfo }`

### 6. `api/chat_routes.py`

- `POST /chat` — auth-protected. Extracts `user_id` from the JWT dependency (never trust a client-supplied `user_id`). Calls `run_rag_query()`, saves the turn via `chat_service`, returns the response.
- Support `?stream=true` to return an SSE stream of the answer text, followed by a final event containing the structured citations and usage data once generation completes.
- `GET /chat/history?project_id=...` — returns paginated chat history for a project, for the frontend chat window.

### 7. Config additions

Add to `.env` / `settings.py`:
- `LLM_PROVIDER=openai` (or `llama`, `gemini`)
- `LLM_MODEL=gpt-4o-mini` (or equivalent — pick a cost-effective model for development)
- `RETRIEVAL_SCORE_THRESHOLD=0.3`
- `CHAT_HISTORY_TURNS=5`
- `LLM_TEMPERATURE=0.2`

## Testing requirements

Write `tests/test_prompt_builder.py`:
1. Confirm chunks are correctly formatted with source labels
2. Confirm chat history is included and correctly ordered
3. Confirm the JSON-output instruction is present in every generated prompt

Write `tests/test_rag_pipeline.py` (mock the LLM and vector store calls):
1. Low-similarity retrieval triggers the guardrail and skips the LLM call entirely
2. A normal query returns a well-formed `{answer, citations}` structure
3. Malformed LLM JSON output triggers the retry path and doesn't crash the pipeline
4. Chat history is saved after a successful query and retrievable via `get_recent_history`

## Manual verification steps (do these after implementation)

1. Upload a paper (existing pipeline), ask a direct factual question about it via `POST /chat` — confirm the answer is grounded and citations reference the correct paper/page/section.
2. Ask a question clearly unrelated to any uploaded paper — confirm you get the "not found" response, not a hallucinated answer.
3. Ask a question, then ask a follow-up using a pronoun ("compare it with X") — confirm the second answer correctly resolves the reference using chat history.
4. Test `?stream=true` — confirm tokens arrive incrementally and citations arrive as a final structured block, not broken mid-stream.
5. Check `GET /chat/history` returns the conversation in order.
6. Deliberately lower `RETRIEVAL_SCORE_THRESHOLD` to 0 and confirm irrelevant chunks now get sent to the LLM — then restore it, to confirm the guardrail is actually doing something (not just a no-op).
